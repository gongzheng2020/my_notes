### TCP三次握手

#### 一、核心目标

> **双方确认各自的发送和接收能力正常，同步初始序列号（ISN）。**

#### 二、三次握手流程（必背）

|次数|发送方|发送内容|状态变化|
|---|---|---|---|
|**第一次**|客户端|`SYN=1, seq=x`（不携带数据，消耗1个序号）|客户端 → `SYN_SENT`|
|**第二次**|服务端|`SYN=1, ACK=1, seq=y, ack=x+1`（不携带数据，消耗1个序号）|服务端 → `SYN_RCVD`|
|**第三次**|客户端|`ACK=1, seq=x+1, ack=y+1`（可携带数据，**不消耗**序号）|双方 → `ESTABLISHED`|

![[Pasted image 20260705141048.png]]

> SYN 和 ACK 是 TCP 数据包头部（Header）中的**两个标志位（Flags）、ack是确认序号**。
> **前两次握手（SYN 和 SYN-ACK）不携带数据**，仅包含 TCP 头部；**第三次握手的 ACK 报文默认也不带数据**，但协议允许客户端在此时捎带应用层数据，以实现性能优化。

![[Pasted image 20260705140528.png]]

- **握手过程中的序号变化**
	- **第一次握手**：客户端发送 `SYN`，并随机生成一个初始序号（比如 `Seq = 100`）。
	- **第二次握手**：服务端回复 `SYN + ACK`，确认号 = **`101`**（说明：`确认号 = 收到的 Seq + 1`，因为 SYN 标志位要**消耗掉一个序号**）。
	- 同时，服务端也随机生成自己的初始序号（比如 `Seq = 200`）。
	- **第三次握手**：客户端回复 `ACK`，确认号 = **`201`**（说明：服务端的 SYN 也消耗了一个序号，所以 `200+1=201`）。



#### 三、为什么必须是三次？（高频核心追问）

1. **核心原因**：**防止已失效的历史连接请求（延迟的旧 SYN 报文）导致服务器误开无效连接，浪费服务器资源。**
    
    - 若只有两次握手，服务器收到延迟的旧 SYN 后会误以为客户端想建立新连接，于是进入等待状态，造成**半开连接**（资源浪费）。
        
    - **三次握手的“妙处”**：客户端收到服务器的 SYN-ACK 后，会检查确认号 `ack` 是否是自己期望的。如果不是（比如是旧连接的），客户端会发送 `RST` 报文拒绝连接，服务器收到后释放资源。
        
2. **为什么不能是两次？**
    
    - **无法防历史**：无法区分当前请求是否是延迟的旧请求。
        
    - **无法确认能力**：服务器无法确认客户端的接收能力是否正常（第三次握手就是用来确认客户端能接收）。
        
3. **为什么不是四次？**
    
    - 三次已经足够**同步双方序列号**并确认双方收发能力正常；四次握手仅增加一次不必要的往返延迟，无额外收益。

#### 四、补充细节（面试加分项）

1. **SYN 洪水攻击**：恶意客户端只发第一次握手（`SYN`），不回复第三次握手（`ACK`），导致服务器堆积大量 `SYN_RCVD` 状态的半连接，耗尽资源。**防范手段**：`SYN Cookies`（Linux 默认开启）。
    
2. **保活计时器**：连接建立后，若长时间无数据交互，服务器会定期发送探测报文。若连续发送 **10 次** 无响应，则判定客户端已断开，关闭连接，防止资源浪费。

#### 五、记忆口诀

> **一发 SYN，二回 SYN-ACK，三送 ACK 建立连。**  
> **消耗序号防旧包，防浪费，第三次不可少。**

### 四次挥手

#### 一、核心目标

> **双方独立关闭各自的数据传输通道，确保所有数据完整传输完毕。**

#### 二、四次挥手流程（必背）

|次数|发送方|发送内容|状态变化|
|---|---|---|---|
|**第一次**|客户端|`FIN=1, seq=u`（不携带数据，消耗1个序号）|客户端 → **`FIN-WAIT-1`**（停止发送数据）|
|**第二次**|服务端|`ACK=1, seq=v, ack=u+1`|服务端 → **`CLOSE-WAIT`**  <br>客户端 → **`FIN-WAIT-2`**|
|**第三次**|服务端|`FIN=1, ACK=1, seq=w, ack=u+1`（消耗1个序号）|服务端 → **`LAST-ACK`**（数据处理完，发起关闭）|
|**第四次**|客户端|`ACK=1, seq=u+1, ack=w+1`|服务端 → **`CLOSED`**  <br>客户端 → **`TIME-WAIT`**（等待 **2MSL** 后关闭）|

#### 三、为什么必须是四次？（高频核心追问）

1. **根本原因：TCP 是全双工的，要确保双方均关闭通道**
    
    - 第一次挥手（客户端发 `FIN`）只代表**客户端不再发送数据**，但服务端**可能还有数据没发完**。
        
    - 所以服务端必须先回复 **`ACK`**（第二次挥手）表示“收到你的关闭请求，等我发完剩下的数据”。
        
    - 服务端数据发完后，才发送自己的 **`FIN`**（第三次挥手）。
        
    - **结论**：**第二次（ACK）和第三次（FIN）必须分开发送，不能合并（如果合并，就等于强迫服务端立即中断未发送的数据）。**
        
2. **为什么必须等 2MSL（TIME-WAIT 状态）？**
    
    - **防止最后一次 ACK 丢失**：如果第四次挥手的 `ACK` 丢了，服务端会超时重发 `FIN`（第三次）。客户端在 `TIME-WAIT`（等待 2MSL，最长报文生存时间）期间能收到重发的 `FIN`，并再次回复 `ACK`，确保服务端正常关闭。
        
    - **防止旧数据包干扰新连接**：确保本次连接的所有数据包都在网络中彻底消失（避免它们污染后续使用相同**四元组(源 IP, 源端口, 目的 IP, 目的端口)**的新连接）。
        
3. **不能是三次？不能是五次？**
    
    - **三次**：无法让服务端在收到 `FIN` 后继续发送未发送的数据，强制中断数据流。
        
    - **五次**：四次已经足够可靠关闭双向连接，多一次无意义，只会增加延迟。

#### 四、状态转换速记（必背）

- **客户端状态链**：`ESTABLISHED` → `FIN-WAIT-1` → `FIN-WAIT-2` → `TIME-WAIT` → `CLOSED`
    
- **服务端状态链**：`ESTABLISHED` → `CLOSE-WAIT` → `LAST-ACK` → `CLOSED`
    

#### 五、面试追问速答

- **Q: 服务端处于 `CLOSE-WAIT` 状态时在做什么？**  
    **A:** 等待应用层处理完剩余的数据，并决定是否关闭连接。如果程序代码没写好（如 Socket 未调用 `close`），大量连接会停留在 `CLOSE-WAIT` 状态，造成资源泄漏。
    
- **Q: 第三次挥手为什么既有 `FIN` 又有 `ACK`？**  
    **A:** `ACK` 是对客户端第一次 `FIN` 的确认；`FIN` 是服务端此时要关闭自己的发送通道，起到“最后一次确认+请求关闭”的双重作用。
    

#### 六、记忆口诀

> **一发 FIN，二回 ACK，三发 FIN-ACK，四送 ACK 关闭连。**  
> **状态转换要牢记：客户端到 TIME-WAIT，服务端走 LAST-ACK。**  
> **全双工关闭分两次，2MSL 防丢保安全。**

### TCP可靠性机制

#### 一、核心目标

> **准确、有序、不丢失、不重复地把数据送达接收端。**

#### 二、7 大核心机制速记（必背）

|机制|一句话核心作用|
|---|---|
|**序列号（Seq）**|**定序、去重、判丢**：给每个字节编号，接收方据此拼回乱序的数据，丢弃重复包，发现丢失包。|
|**确认应答（ACK）**|**报平安**：接收方告知发送方“我已收到 XX 之前的所有数据”（累积确认），作为下一段数据发送的依据。|
|**重传机制**|**补发**：数据或 ACK 丢失时重新发送。包含**超时重传**（等不到 ACK 就发）和**快速重传**（收到 3 个重复 ACK 立刻发）。|
|**校验和（Checksum）**|**验货**：发送方算一次，接收方算一次。不一致说明比特错误，直接丢弃，触发发送方重传。|
|**连接管理**|**建立/关闭通道**：三次握手（同步 ISN，确保双方就绪），四次挥手（全双工独立关闭，确保数据完整）。|
|**流量控制**|**防压垮接收方**：接收方通过滑动窗口告知发送方“我还有多少空间”（`rwnd`），动态调整发送速度。|
|**拥塞控制**|**防堵死网络**：发送方通过感知丢包/延迟，用慢启动、拥塞避免等算法动态调整速率（`cwnd`），避免路由器过载。|

---

#### 三、重传机制区分（高频面试点）

|重传类型|触发条件|特点|
|---|---|---|
|**超时重传**|重传计时器（RTO）超时，未收到 ACK|最基础，但往往反应较慢（耗时较长）。|
|**快速重传**|收到 **3 次重复 ACK**（冗余 ACK）|不必等超时，提前发现丢包，效率更高。|

---

#### 四、流量控制 vs 拥塞控制（最容易混淆的知识点）

|对比维度|**流量控制（点对点）**|**拥塞控制（全局）**|
|---|---|---|
|**关注对象**|接收方的处理能力（缓冲区大小）|整个网络的承载能力（路由器是否拥塞）|
|**控制窗口**|**接收窗口（`rwnd`）**|**拥塞窗口（`cwnd`）**|
|**核心算法**|滑动窗口|慢启动、拥塞避免、快速恢复、快速重传|
|**最终效果**|发送方速率 ≈ 接收方处理速率|发送方速率 ≈ 网络能承受的速率|

>**拥塞控制**：发送方通过**动态调整发送速率**，防止过多数据注入网络导致路由器过载，保证网络稳定和公平性。

---

#### 五、面试追问速答

- **Q: TCP 为什么要用“累积确认”？**  
    **A:** 提高效率。发送方不需要为每个包都确认一次，只要收到 ACK 号为 `n`，就代表 `n` 之前的所有数据都已安全到达。
    >ACK号指**“接下来期望接收到的第一个字节的序号”**
    
- **Q: 快速重传为什么能省时间？**  
    **A:** 它通过检测重复 ACK，在计时器超时**之前**就推测出丢包并提前重传，减少了等待时间。
    

#### 六、记忆口诀

> **序列号排序去重，ACK 报收确认，重传兜底补丢包，校验和防比特错。**  
> **三次握手建连接，四次挥手安全关。**  
> **流量控接收方，拥塞控网络态，双方联动保可靠。**

### TCPKeepalive和HTTPKeep-Alive的区别？

#### 一、核心定义（一句话分清）

- **TCP Keepalive**（传输层）：由**操作系统内核**管理，目的是**检测长时间空闲的 TCP 连接是否还活着**（防僵尸连接）。
    
- **HTTP Keep-Alive**（应用层）：由**应用程序（浏览器/服务器）**管理，目的是**复用同一个 TCP 连接发送多个 HTTP 请求**（防重复握手，提高效率）。
    

#### 二、核心对比表（必背）

|对比维度|**TCP Keepalive**|**HTTP Keep-Alive**|
|---|---|---|
|**协议层**|传输层（TCP）|应用层（HTTP）|
|**主要目的**|**检测存活性**（对方还在不在）|**复用连接**（减少三次握手开销）|
|**触发时机**|连接长时间**空闲**（如默认 2 小时）|**HTTP 事务完成**后（决定是否保持）|
|**管理方**|**操作系统内核**|**HTTP 客户端/服务器**|
|**控制方式**|内核参数（`sysctl`）/ Socket 选项|HTTP 头（`Connection`）/ Web 服务器配置|
|**传输内容**|空探测报文（仅 TCP 头，无数据）|实际的 HTTP 请求/响应数据|

#### 三、两者关系（面试加分点）

> **两者是不同层次、独立工作但协同配合的机制。**

- **HTTP 依赖 TCP**：`HTTP Keep-Alive` 决定暂时**不关闭**底层的 TCP 连接。
    
- **TCP 兜底检测**：如果这个连接长时间没有新的 HTTP 请求，底层 TCP 就会因**长时空闲**而触发 `TCP Keepalive` 机制，发送探测包确认对方是否还活着。
    
- **一句话总结**：**HTTP 负责“复用省时”，TCP 负责“确保活着”。**
    

#### 四、高频追问速答

- **Q: 如果服务端进程崩溃了，客户端什么时候会知道？**  
    **A:** 正常情况下，客户端在`HTTP Keep-Alive`超时后可能尝试复用连接。如果底层`TCP Keepalive`未设置，客户端可能等很久才超时报错；如果设置了`TCP Keepalive`，内核会在探测失败后快速通知应用层，客户端就能及时感知到服务端已崩溃。
    
- **Q: 为什么 `TCP Keepalive` 默认时间很长（如 2 小时）？**  
    **A:** 因为频繁发送探测报文会占用网络带宽和 CPU，默认设长一点是为了“不要轻易打扰正常运行的连接，只在极端空闲时兜底检测”。
    

#### 五、记忆口诀

> **TCP 内核探死活，超时空闲发探测；**  
> **HTTP 应用复用连，事务完成不断线。**  
> **二者协同不同层，忙时 HTTP 控，闲时 TCP 探。**
