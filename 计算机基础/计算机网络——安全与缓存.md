### HTTP和HTTPS的区别

#### 一、核心定义（一句话区分）

> **HTTP 是明文传输，HTTPS 是 HTTP 的安全加密版。** HTTPS 在 HTTP 和 TCP 之间加了一层 **SSL/TLS 协议**，实现了加密传输、数据完整性和服务器身份认证。

#### 二、核心对比表（必背）

|对比维度|**HTTP**|**HTTPS**|
|---|---|---|
|**加密与安全性**|**明文传输**，易被窃听和篡改|**SSL/TLS 加密**，确保机密性 + 完整性|
|**默认端口**|**80**|**443**|
|**身份认证**|无验证（任何人都可伪装服务器）|**CA 数字证书**，验证服务器身份，防钓鱼|
|**协议强制要求**|HTTP/1.1/2 可选明文，但浏览器不推荐|HTTP/2 默认需 HTTPS；**HTTP/3 强制使用 HTTPS**|
|**浏览器标识**|标记为**“不安全”**（如红色警告）|显示 **“安全锁”** 标志，提升用户信任|
|**SEO 排名**|搜索引擎降权|搜索引擎**优先排名**（Google 明确宣导）|

#### 三、深入理解：SSL/TLS 提供了哪三重保障？（面试追问点）

1. **加密（机密性）**：使用对称加密（如 AES）加密传输数据，即使被截获也只是一串乱码。
    
2. **完整性**：使用哈希算法（如 SHA-256）对数据做摘要验证，确保数据在传输途中未被篡改。
    
3. **身份认证**：服务器必须持有由可信 **CA（证书颁发机构）** 签发的数字证书。浏览器会自动验证证书链是否合法、证书是否过期，从而确保你访问的是**真实的目标服务器**，而非中间人伪装的钓鱼网站。

#### 四、面试高频追问速答

- **Q: HTTPS 比 HTTP 慢吗？**  
    **A:** 第一次连接会有额外的 **TLS 握手开销**（通常多 1~2 个 RTT 延迟），但现代协议（如 TLS 1.3 支持 0-RTT 快速握手）和硬件加速已极大优化了性能，且 HTTP/2、HTTP/3 的诸多优点都依赖 HTTPS，实际综合体验远优于明文 HTTP。
    
- **Q: 什么是混合内容（Mixed Content）？**  
    **A:** 当 HTTPS 网页里加载了 HTTP 资源（如图片、脚本），浏览器会视为“不安全”并直接拦截。**现代浏览器强制要求 HTTPS 页面内的所有资源也必须使用 HTTPS。**
    
- **Q: 为什么 HTTP/3 强制要求 HTTPS？**  
    **A:** HTTP/3 基于 **QUIC 协议**（UDP 之上），其设计初衷就是将 **TLS 1.3 加密和传输层握手合并**，意味着连接建立时就已经完成了加密协商，因此 HTTP/3 天然就是加密的，不存在明文的 HTTP/3。
    
- **Q: 证书有哪几种类型？**  
    **A:** DV（域名验证，只验证域名所有权，最常用）、OV（组织验证，验证企业资质）、EV（扩展验证，地址栏显示绿色企业名称，现已逐步淡化）。
    

#### 五、记忆口诀

> **HTTP 裸奔不安全，HTTPS 加锁防篡改。**  
> **明文用 80，加密走 443。**  
> **证书认证防钓鱼，浏览器把锁标记。**  
> **HTTP/2 默认要加密，HTTP/3 彻底抛弃明。**

### HTTPS的工作原理

#### 一、核心定义

> **HTTPS = HTTP + SSL/TLS 加密层**（默认端口 **443**）。它解决了 HTTP 的三大安全问题：**窃听**（加密）、**篡改**（完整性校验）、**冒充**（身份认证）。

#### 二、完整工作流程（4个阶段）

> **建立 TCP 连接 → TLS 握手协商密钥 → 加密通信 → 断开连接**

#### 三、TLS 握手 8 步流程（详细拆解）

![[Pasted image 20260706201834.png]]

|步骤|阶段|核心动作|关键点|
|---|---|---|---|
|**1. Client Hello**|客户端|发送支持的 **TLS 版本**、加密套件列表、**客户端随机数**|表明“我支持这些加密方式”|
|**2. Server Hello**|服务端|选择加密套件，发送**服务器随机数**|双方各持一个随机数，确保每次会话不同|
|**3. Certificate**|服务端|发送自己的 **数字证书**（含**公钥**、域名、签发CA）|相当于服务器的“身份证”|
|**4. Certificate Verify**|客户端|验证证书是否受信任、域名匹配、是否过期|防钓鱼网站的关键一步|
|**5. Key Exchange**|客户端|生成 **预主密钥**，用**证书公钥**加密后发给服务器|使用**非对称加密**传输预主密钥|
|**6. Session Key Gen.**|双方|双方用两个随机数 + 预主密钥，生成**会话密钥**|后续通信将使用这个**对称密钥**|
|**7. Change Cipher Spec**|双方|通知对方“后续消息开始用会话密钥加密”|切换加密模式|
|**8. Finished**|双方|发送握手完成消息，校验整个握手过程无误|握手结束，开始正式传输数据|

#### 四、混合加密机制（高频核心追问）

**面试必问：为什么 TLS 握手用非对称加密，而数据传输用对称加密？**

|加密方式|使用阶段|特点|原因|
|---|---|---|---|
|**非对称加密**（RSA/ECC）|**TLS 握手阶段**|慢、安全|用于**安全交换预主密钥**，防止中间人窃取。公钥加密，私钥解密，只有服务器能解开。|
|**对称加密**（AES/ChaCha20）|**数据传输阶段**|极快、效率高|用于**加密大量业务数据**，保证用户体验和吞吐量。|

> **一句话总结**：握手用“非对称”来“安全递送钥匙”，通信用“对称”来“快速开箱取货”。

#### 五、HTTP/3 的 HTTPS 握手区别（知识拓展）

- **底层协议**：HTTP/3 基于 **QUIC（UDP）**，而不是 TCP。
    
- **握手过程**：QUIC **强制内置 TLS 1.3**，不需要先建 TCP 再建 TLS，而是**合并为一个握手**。首连接只需 **1-RTT**，后续连接可实现 **0-RTT**（第一个数据包即可携带应用数据），极大降低首屏延迟。
    
- **结论**：HTTP/3 天然只支持 HTTPS，不存在“明文 HTTP/3”。
    

#### 六、记忆口诀

> **HTTP 明文不安全，加层 SSL 变 HTTPS。**  
> **握手八步协商密钥，验证证书防钓鱼。**  
> **公钥加密传私钥，会话密钥靠两组随机数。**  
> **非对称安全传钥匙，对称高效传数据。**  
> **HTTP/3 放弃 TCP，QUIC 一步达 0-RTT。**

### HTTP缓存机制

#### 一、核心定义

- **强缓存**：浏览器判断本地缓存**未过期**，**不发送任何请求**，直接使用本地资源（状态码 `200 (from disk/memory cache)`）。
    
- **协商缓存**：强缓存**失效**后，浏览器向服务器发送请求**验证**。若资源未变，服务器返回 `304`，浏览器继续使用本地缓存；若已变，返回 `200` 和新资源。
    

#### 二、核心对比表（必背）

|对比维度|**强缓存**|**协商缓存**|
|---|---|---|
|**是否发请求**|❌ **不发送**任何网络请求|✅ **发送**请求给服务器验证|
|**状态码**|`200 (from cache)`|`304 Not Modified` 或 `200 OK`|
|**控制头（关键）**|`Cache-Control`（HTTP/1.1）  <br>`Expires`（HTTP/1.0）|`Last-Modified` / `If-Modified-Since`  <br>`ETag` / `If-None-Match`|
|**适用场景**|静态资源（CSS、JS、图片）|动态资源、实时更新的 API 数据|

#### 三、执行流程（面试必考）

![[Pasted image 20260706202328.png]]

> **先判断强缓存 → 若失效，再走协商缓存。**

#### 四、关键头字段区分（高频易错点）

**1. `Cache-Control` vs `Expires`**

|对比|`Cache-Control`（HTTP/1.1）|`Expires`（HTTP/1.0）|
|---|---|---|
|**时间基准**|**相对时间**（如 `max-age=3600`）|**绝对时间**（GMT 格式）|
|**优先级**|**高**（若同时存在，覆盖 Expires）|低|
|**致命问题**|无（不依赖客户端时钟）|依赖客户端时间，时差会导致缓存异常|

> **记忆口诀**：**1.1 的 `Cache-Control` 优先、相对、不依赖客户端时间。**

**2. `ETag` vs `Last-Modified`**

|对比|`Last-Modified`|`ETag`|
|---|---|---|
|**验证依据**|文件**最后修改时间**（秒级）|文件内容的 **哈希值/唯一标识符**|
|**精度问题**|1 秒内多次修改无法检测|内容一改，哈希必变（支持毫秒/微秒级变化）|
|**优先级**|低|**高**（若同时存在，ETag 优先）|

> **为什么需要 `ETag`？** 解决 `Last-Modified` 的两个致命缺陷：① 1 秒内多次修改无法识别；② 文件被修改但内容不变（如还原旧版本），时间戳变了但内容没变，`ETag` 能准确识别“内容未变，无须更新”。

#### 五、记忆口诀

> **强缓存不发包，200 本地取；协商缓存发验证，304 用旧，200 换新。**  
> **Cache-Control 相对优先，Expires 绝对靠边；**  
> **Last-Modified 时间不精准，ETag 哈希判断才靠谱。**

### Cookie和Session的区别？

#### 一、核心定义（一句话区分）

- **Cookie**：**浏览器端**的存储载体（存字符串或 Session ID），用于解决 HTTP 无状态，由服务器 `Set-Cookie` 下发，浏览器 `Cookie` 自动带回。
    
- **Session**：**服务端**的会话状态（存复杂对象/敏感数据），通过唯一 ID（通常存在 Cookie 中）关联用户请求。
    

#### 二、核心对比表（必背）

|对比维度|**Cookie**|**Session**|
|---|---|---|
|**存储位置**|**浏览器端**（用户可见可修改）|**服务器端**（内存/Redis/数据库）|
|**安全性**|较低（易被 **XSS** 窃取、**CSRF** 利用）|较高（敏感数据在服务端，只有 Session ID 暴露）|
|**数据类型**|仅 **字符串**（需序列化如 JSON）|**任意对象**（Java 对象、PHP 数组等）|
|**生命周期**|默认会话级，可设 `Max-Age` 长期有效|通常随会话结束失效，服务端可配置超时（如 Tomcat 的 `session-timeout`）|
|**性能影响**|每次请求携带，增加**带宽消耗**|占用**服务器内存**，高并发需用 Redis 集群|

#### 三、协作关系（工作原理）

![[Pasted image 20260706203308.png]]

> **`Cookie` 是传信的，`Session` 是存信的。**

1. **首次请求**：服务器生成一个唯一的 **Session ID**。
    
2. **下发**：通过 `Set-Cookie: JSESSIONID=abc123` 将 Session ID 种到浏览器的 Cookie 中。
    
3. **回传**：后续请求，浏览器自动通过 `Cookie: JSESSIONID=abc123` 把 ID 带回服务端。
    
4. **恢复状态**：服务端根据 ID 在内存/Redis 中查找到对应的 Session 数据（如用户名、购物车）。

#### 四、面试追问速答（进阶加分项）

- **Q: 如果浏览器禁用了 Cookie，Session 还能用吗？**  
    **A:** 可以，使用 **URL 重写**（在 URL 后面追加 `;jsessionid=abc123`）或直接使用 **Token/JWT** 替代。
    
- **Q: 分布式环境下 Session 如何共享？**  
    **A:** 传统的单机 Session 在多服务器下无法共享，现代方案是：
    
    1. **集中存储**：使用 Redis 作为独立的 Session 存储层，多台服务器统一读写 Redis。
        
    2. **无状态化（JWT）**：直接将用户信息编码加密进 Token，服务端不存 Session，完全解耦。
        
- **Q: Cookie 的 `HttpOnly` 和 `SameSite` 属性有什么用？**  
    **A:** `HttpOnly` 防止 JavaScript 读取 Cookie（防御 **XSS**）；`SameSite` 限制跨站携带 Cookie（防御 **CSRF**）。
    

#### 五、记忆口诀

> **Cookie 客户端存字符串，Session 服务端存对象。**  
> **Cookie 携 ID 找 Session，核心状态不落浏览器。**  
> **高并发用 Redis 集中存，无状态推荐 JWT。**
