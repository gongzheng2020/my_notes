### HTTP 1.0与1.1的区别

#### 一、核心定义（一句话区分）

- **HTTP/1.0**：默认**短连接**。每次请求都需重新建立 TCP 连接，性能开销大。
    
- **HTTP/1.1**：默认**长连接**（持久连接）。复用同一个 TCP 连接处理多个请求，效率大幅提升。

#### 二、核心区别对比表（必背）

|对比维度|**HTTP/1.0**|**HTTP/1.1**|
|---|---|---|
|**默认连接**|**短连接**（需手动 `Connection: keep-alive` 开启）|**长连接**（标准内置，默认持久化）|
|**Host 头**|❌ **不支持**（无法单 IP 托管多域名）|✅ **支持**（虚拟主机核心技术，单 IP 多域名）|
|**分块传输**|❌ **不支持**（需预先知道 Content-Length）|✅ **支持**（动态内容流式传输 `Transfer-Encoding: chunked`）|
|**缓存机制**|仅 `Expires`（绝对时间） / `Last-Modified`（修改时间）|新增 **`Cache-Control`**（相对时间） / **`ETag`**（哈希值）|
|**队头阻塞（HOL）**|❌ **无**（短连接每次独立请求）|⚠️ **存在**（长连接下的管道化需按序响应，首个慢请求会阻塞后续）|
|**范围请求**|❌ **不支持**（必须下载完整资源）|✅ **支持**（断点续传、视频拖动播放）|
|**状态码**|基础状态码（如 200、404）|大幅扩展（新增 100、409、410 等 40+ 种）|

#### 三、高频追问速答（易混淆点）

- **Q: 为什么说 HTTP/1.1 存在“队头阻塞”？**  
    **A:** HTTP/1.1 支持**管道化（Pipelining）**，允许客户端不等响应就接连发多个请求，但**服务器必须按请求顺序串行返回响应**。如果第一个请求处理非常耗时（如复杂数据库查询），后续的所有响应都会在它后面排队等待，造成“队头阻塞”。（实际浏览器默认禁用此功能）。
    
- **Q: HTTP/1.0 和 HTTP/1.1 的缓存机制有什么本质区别？**  
    **A:** 1.0 用绝对时间（`Expires`），依赖客户端时钟，可能不准确；1.1 新增了**相对时间**（`Cache-Control: max-age`）和**文件哈希校验**（`ETag`），缓存控制更精确高效。
    
- **Q: `Host` 头为什么至关重要？**  
    **A:** HTTP/1.1 强制要求携带 `Host` 头（如 `Host: www.example.com`），这使得**一台物理服务器（一个 IP）可以同时托管多个不同域名的网站**，是现代云计算和虚拟主机的基石。
    

#### 四、记忆口诀

> **1.0 短连效率低，1.1 长连复用强。**  
> **Host 虚拟主机立，分块动态流式传。**  
> **缓存 ETag 精准控，范围请求断点续。**  
> **管道排队有阻塞，2.0 多路能打破。**

### HTTP_2.0与HTTP_1.1相比有哪些主要改进？

#### 一、核心五大特性

> **二进制分帧、多路复用、头部压缩、流优先级、服务器推送**

#### 二、五大特性对比表（必背）

|特性|解决 HTTP/1.1 的问题|改进方案|核心效果|
|---|---|---|---|
|**1. 多路复用**|**队头阻塞**（请求串行排队，慢请求阻塞后续）|**二进制分帧**，每个帧带 `Stream ID`，不同流的帧可**并行交错**发送|单个 TCP 连接高效并行传输，大幅降低延迟|
|**2. 头部压缩**|**头部冗余**（重复的 User-Agent、Cookie 浪费带宽）|**HPACK 算法**（静态字典 + 动态字典 + Huffman 编码）|头部体积减小 **50%~90%**，弱网环境提升显著|
|**3. 二进制协议**|**文本解析慢**（基于换行符，解析效率低）|改用**二进制帧**，帧头固定格式（类型、长度、流 ID）|解析速度更快，支持帧级别的高级控制|
|**4. 流优先级**|**资源加载顺序不可控**（非关键资源阻塞首屏）|通过**权重和依赖关系**（树状结构）定义优先级|**首屏资源**（如 HTML、CSS）优先加载，提升用户体验|
|**5. 服务器推送**|**额外 RTT 延迟**（解析 HTML 后才发现 CSS/JS，需再发请求）|服务器在响应主资源（如 HTML）时**主动推送**关联资源（如 CSS）|提前加载关键资源，减少往返延迟，客户端可发 `RST_STREAM` 拒绝冗余推送|

#### 三、高频考点：HPACK 压缩（核心技术细节）

> **静态表 + 动态表 + Huffman 编码**（三合一）

1. **静态字典**：预定义了 **61 个** 最常见的 HTTP 头部（如 `:method: GET`、`accept-encoding: gzip`），直接用 **索引（数字）** 代替长字符串传输。
    
2. **动态字典**：在通信过程中**动态缓存**自定义或不在静态表中的头部字段（如自定义 `X-Token`），后续请求复用索引。**大小有限**，遵循 LRU（最近最少使用）淘汰机制。
    
3. **Huffman 编码**：对字符串进行二次压缩，**高频字符用短编码，低频字符用长编码**，进一步压缩体积。
    

#### 四、面试追问速答

- **Q: HTTP/2 的多路复用解决了什么问题？**  
    **A:** 彻底解决了 HTTP/1.1 的**队头阻塞**问题。它不依赖串行排队，而是将消息拆为带 `Stream ID` 的帧，多个帧在同一个 TCP 连接上**乱序并行**传输，最后在接收端按流 ID 重组。
    
- **Q: HTTP/2 还有队头阻塞吗？**  
    **A:** 有，但发生在**底层 TCP**。虽然 HTTP/2 解决了**应用层（HTTP）**的队头阻塞，但由于它仍基于 TCP，如果 TCP 层面发生丢包，整个 TCP 连接还是会阻塞等待重传。这也是 **HTTP/3 推出（基于 UDP 的 QUIC 协议）** 的原因之一。
    
- **Q: 服务器推送的优势是什么？**  
    **A:** 关键在于**减少 RTT（往返时间）**。浏览器不需要先解析 HTML 再去请求 CSS/JS，服务端直接一起发过来，显著缩短首屏加载时间。
    

#### 五、记忆口诀

> **多路复用破队头，二进制帧高速传；**  
> **HPACK 压缩省带宽，静态动态加哈夫；**  
> **优先级控首屏快，服务端推减 RTT。**

### HTTP如何实现多个TCP连接？

#### 一、核心演进脉络

> **HTTP/1.1：用「多个 TCP 连接」并发 → HTTP/2：用「单个 TCP 连接多路复用」优化 → HTTP/3：彻底「抛弃 TCP，改用 QUIC」。**

#### 二、三阶段核心对比表（必背）

|特性|**HTTP/1.1 连接池**|**HTTP/2 多路复用**|**HTTP/3 (QUIC)**|
|---|---|---|---|
|**底层协议**|TCP|TCP|**UDP** (基于 QUIC)|
|**连接方式**|**多个连接**并行（默认 6-8 个）|**单个连接**并行交错发送多个帧|单个 QUIC 连接|
|**解决队头阻塞**|⚠️ **部分解决**（跨连接隔离，但单连接内串行）|✅ **应用层解决**（基于 Stream ID，请求/响应完全交错）|✅ **传输层彻底解决**（丢包只影响单个流）|
|**连接开销**|❌ 大（每个连接都需 TCP+TLS 握手）|✅ 小（只需 1 次握手）|✅ **极小**（支持 0-RTT，合并 TLS 握手）|
|**头部压缩**|不支持（明文无压缩）|✅ **HPACK**（静态+动态表）|✅ **QPACK**（支持乱序传输动态表）|
|**额外特征**|需手动控制连接池大小|流优先级、服务器推送|天然强制加密，快速重连|

#### 三、核心痛点与解决逻辑（面试必问）

**Q: HTTP/1.1 为什么还要建立多个 TCP 连接？**

> 因为 HTTP/1.1 是**串行阻塞**的（队头阻塞）。浏览器为了规避这个问题，强行给同一个域名开了 **6-8 个 TCP 连接**。虽然能并发下载，但每个连接独立做三次握手+TLS握手，非常浪费资源，且互相竞争带宽。

**Q: 为什么 HTTP/2 解决了队头阻塞，但 HTTP/3 还要换成 UDP？**

> HTTP/2 解决的是 **应用层（HTTP）** 的队头阻塞。由于它仍运行在 TCP 之上，如果 TCP 层面发生**丢包**，整个 TCP 连接（包含所有流）都会停下来等重传（**TCP 队头阻塞**）。HTTP/3 彻底改用基于 **UDP 的 QUIC**，丢包只会影响对应的单个数据流，其他流完全不受影响，从而实现了**传输层的彻底多路复用**。

#### 四、面试追问速答

- **Q: 浏览器默认同一个域名开多少个连接？**  
    **A:** 不同浏览器略有差异，**通常为 6-8 个**，HTTP/2 之后改为单个连接多路复用。
    
- **Q: 为什么 HTTP/3 的“0-RTT”很关键？**  
    **A:** 传统的 TCP + TLS 建立连接需要 2-3 个 RTT（往返时间）。HTTP/3 的 QUIC 将 TLS 握手合并到连接建立过程中，首次连接 1-RTT，后续连接可以实现 **0-RTT**，即前一个数据包就能携带应用数据，大幅降低首屏加载延迟。

#### 五、记忆口诀

> **1.1 多连排队堵，6-8 个硬并发；**  
> **2.0 单连混着发，多路复用破队头；**  
> **3.0 彻底换 QUIC，丢包不碍其他流，0-RTT 更快速。**
